## What is established

| Concern | Evidence and limit |
|---|---|
| Programmatic orchestration | Both already expose code orchestration and filtered tool results. Pi codemode runs fresh QuickJS async scripts; Prime uses a persistent CPython `__main__` namespace/event loop. Merely adding code execution is not a novel Suffice treatment. |
| Existing small state | Installed `@earendil-works/pi-coding-agent` 1.2.0 `docs/codemode.md` documents `store/load`: successful writes append session custom entries, resumed sessions retain values, branches see their own path. Limits: 262,144 JSON characters/value; 1,048,576 overall. Failed scripts do not commit writes. This is more than a stateless tool wrapper. |
| Actual Suffice actor lifetime | `src/harness.mjs:251-263`, `src/real-agent.mjs:106-112`, and `src/workflow-agent.mjs:59-64` use in-memory settings/sessions and disable automatic compaction. Small state can survive calls within that actor, but those actors do not thereby acquire durable cross-process recovery. Explicit experimental context policies are a separate treatment. |
| Prime state | `repl.md` and `repl.py` describe persistent Python variables and per-name dill snapshots. Snapshot exclusions, serialization failures, per-variable/aggregate limits, missing/corrupt restores, and skipped/pruned variables matter. This is not unlimited or guaranteed retention. Windows synchronous-code interruption is documented as limited. |
| Compaction | Prime's four compaction files implement summary/retained-tail and kernel-state handling. Its README describes automatic thresholds and input/output ceilings. These are implementation capabilities, not evidence of fewer tokens or better correctness on Suffice tasks. |
| Continual harness | README and `skills/refine/SKILL.md` describe updates to supplemental prompts, memories, skill descriptions, and subagent specifications; refinement defaults to session scope, global scope is explicit. This is harness adaptation, not demonstrated weight training. Rebuilding prompts can affect cache prefixes. |
| Descendant accounting | `rlm_children/usage.rs` includes per-origin usage reporting, retryable pending reports, final emission, and retired-child accounting. That supports a feasible reconciliation design but does not establish completeness through the untested chosen provider. |
| Failed-call accounting caveat | `crates/pa-types/src/usage.rs:36-49` explicitly excludes aborted/error assistant messages in `valid_assistant_usage`. It does not prove every cost path drops them, but makes UI/session aggregates insufficient as the sole spend evidence. |
| Completion gates | `autonomous/gates.rs` evaluates shell gates and budgets, including unchanged-workspace handling. A gate pass only establishes its checked contract; it cannot replace an independent grader. |

## Executable-in-principle preregistration

This is a run specification, not verified CLI syntax. An adapter must first demonstrate each required control and receipt; if it cannot, mark that comparison infeasible rather than silently substituting settings.

1. Freeze task/repository revisions, graders, prompts, package/source hashes, allowed tools, output ceilings, retry policy, and harness revisions. Assign repository/failure-family groups to development, difficulty pilot, and final holdout before policy selection. No near-duplicate issue variants across splits. Keep hidden tests and expected patches outside actor read/write access; grade externally in fresh disposable copies. Blind human adjudication of ambiguous outcomes uses the same rubric for both arms.
2. Compare frozen Suffice core with frozen Prime without cross-task refinement first. Match exact model ID/revision, provider endpoint/account entitlement, reasoning effort, context/output limits, sampling controls where supported, region and concurrency. Every descendant uses the same model/effort; disable model routing. If either harness cannot expose equivalent controls, report an explicitly confounded product comparison, not a harness-only causal claim. Do not equate API prices and subscription entitlement costs.
3. Permit each harness's native orchestration but enforce equal aggregate inference-token/spend, elapsed-time, tool-execution, and concurrent-worker ceilings over the entire task tree. Native prompts/tools remain treatment differences. Keep refinements off in the static comparison; isolate compaction-enabled long tasks as a separate stratum, with common effective window and explicit trigger records. A constrained single-agent arm can be a later ablation, not an unannounced restriction on one competitor.
4. Use a disjoint difficulty pilot (for example 12 repository tasks spanning invariant repair, ambiguous evidence, multi-file edits, and long context). Require both passes and failures in pooled results; if all pass, extend/replace only the pilot before freezing the final set. Set final sample size from paired-discordance estimates and a declared minimum meaningful success/cost difference; choose repetitions to characterize stochastic variation. Do not repeatedly inspect holdout results to increase sample size or tune prompts.
5. Randomize paired task/repetition order in AB/BA crossover blocks and interleave arms in time. Record provider cache-read/write tokens per request, prefix hashes, timestamps and observed warmth. Process restart does not establish a cold provider cache. Use provider-documented isolation/expiry only if available; otherwise label coldness unverified. Separately report first-exposure and naturally warm repeat blocks. Any explicit warm-up uses equal policy and is charged/reported. Do not inject unique text into only one arm to defeat caching. Analyze crossover period/order and cache strata, not one pooled dollar ratio alone.
6. At run start, create isolated source copies and empty task-local harness/session stores. At end, stop/join descendants and background work, capture late usage, freeze patch and logs, and run immutable graders. A killed or detached child remains part of the cost tree. No manual rescue or hidden-test feedback to workers. Match retry/error categories and budgets; automatic reattempts belong to the original scheduled attempt, not extra independent successes.
7. Preserve every scheduled attempt: acceptance fail, overload, timeout, interruption, tool failure, missing usage, corrupted state, and incomplete patch. Report intention-to-treat success over all scheduled attempts, plus diagnostic conditional completion. Keep provider outages visible; any prespecified rerun is an additional paired block while originals remain in the ledger.
8. Build a request-level ledger keyed by task, scheduled attempt, actor/parent, provider request identity, call role, retry index, time, token classes, price provenance, known cost, and unknown-cost flag. Include root, all descendants, refinement, summarization/compaction, classifiers, failed/aborted retries, and warm-ups. Sum unique provider calls once; do not add an inclusive parent aggregate to the same child receipts. Reconcile raw receipts against provider totals where available and session aggregates; unreconciled/unknown spend stays unknown, never zero. Report model computation, tool CPU, wall time, and billed/API-equivalent costs separately.
9. Primary outcomes: paired external acceptance difference and total computation/cost at equal task budgets. Report confidence intervals clustered by repository/task family, paired discordance, success-versus-cost frontier, timeout/error rates, and cost per accepted task with failures charged. Avoid accepted-only mean cost, tool-call count as computation, and ratios with negligible/zero accepted denominators. A selection rule must require reliability preservation as well as cost reduction.

## Separate continual-adaptation experiment

Only after the static comparison is feasible: use identical ordered development task streams, equal refinement opportunity/budget, and fresh stores per replicate. Charge adaptation inference and validation to training-stream totals and report amortized totals over a prespecified horizon. Snapshot before/after changes and preserve rollback history. Freeze adapted stores before untouched holdout tasks; prohibit holdout-derived refinement or feedback. Compare against an unchanged harness with the same model and task stream. Session-local lessons and global cross-session lessons are distinct treatments; neither establishes model training. Report negative transfer and leakage as well as gains.

## Offline evidence to collect before new persistent state or learning

The root `reports/RESEARCH-FINDINGS.json` already records 177 newest codemode programs with direct whole-result emits and no direct store/load calls; this is static occurrence evidence, not proof every emit executed or was wasteful. It also records no exact repeated file-read receipts in specific cohorts, while source reads dominate output characters. Therefore repeated-read avoidance is not yet a demonstrated large benefit.

- Annotate existing programs by raw result size, emitted size, actual execution/error path, useful task evidence, and whether a compact record could answer a later question. Distinguish selection/aggregation from merely hiding source.
- Trace actual future uses of IDs, parsed structures, source excerpts and decisions; measure semantic rediscovery, partial overlaps and cross-actor duplication separately from exact repeated reads. Record source hashes and intervening edits to detect stale-state risks.
- Determine which candidate state fits Pi's existing JSON store and which truly needs persistent objects, recovery, or cross-session durability. Record serialization size/type, provenance, invalidation rules, lifetime, branch ownership and recovery obligations. Availability and non-use do not establish usefulness.
- Manually inspect failed attempts for missing evidence, stale evidence, bad reasoning, interface errors and incorrect completion triggers. The observed directory-path EISDIR mismatch and invariant failures should not be reclassified as memory failures without trace evidence.
- For any proposed lesson, preserve the triggering trajectory, independent correctness evidence, intended applicability, counterexamples, validation result and supersession record. Keep operational telemetry, task-content permission and training permission distinct. Do not train a decision model before representative decisions and an immutable benchmark exist.
