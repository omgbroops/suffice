# Engine migration inventory

This is a source inventory of the existing implementation, not a claim of Rust parity. Every Rust implementation and compatibility check below is **pending**. The production CLI uses `packages/cli`; `packages/harness/index.mjs` re-exports its session and options. Root `src/` and `tests/` primarily implement and exercise research harness variants, which are separate from the CLI product. Desktop callers can supply additional session options and callbacks; their integration must also be inventoried before claiming product-wide parity.

The CLI pins `@earendil-works/pi-coding-agent` 1.5.2. Pi supplies much of the actual agent engine. Paths under `node_modules` below refer to the installed 1.5.2 distribution used for inspection; internal package paths are evidence, not guaranteed public APIs. The package publicly exports its root and `./rpc-entry`.

## Session migration and rollback

Opening an old session can mutate it: Pi migrates v1 linear records to the v2 parent-linked tree, then changes v2 `hookMessage` roles to v3 `custom`, and rewrites the file. Its parser skips malformed JSON lines. A compatibility experiment must therefore never open the only copy of a user's session using either implementation.

Before an in-scope migration test, stop all writers to the selected test session, copy the entire relevant session directory to a separate verified backup, and record relative file names, sizes and cryptographic hashes. Run each implementation against independent copies, then compare both the output and on-disk files. Preserve the untouched backup until verification completes. For rollback, stop writers again and restore from the verified backup to the exact original location, preserving a copy of any newer data before replacement; verify hashes afterward. Do not apply this procedure to real user data without the user's task putting that data in scope. A copy rollback may discard changes made after the snapshot, so reconcile those changes first.

## Embedded JavaScript boundary

An embedded JS interpreter alone is insufficient for existing Pi extensions. Their compatibility surface includes Node built-ins, asynchronous module loading, npm resolution, jiti TypeScript loading and Pi/TypeBox aliases, filesystem and subprocess APIs, networking/streams, workers, timers, native dependencies, event lifecycle and TUI bindings. Codemode is a separate, deliberately constrained QuickJS WASM environment with an explicit asynchronous host bridge and termination semantics. Any embedded approach must reproduce and test both surfaces, or retain Node/Pi as a compatible sidecar. A sidecar preserves the current dependency and startup costs, so performance gains must be measured rather than assumed.
