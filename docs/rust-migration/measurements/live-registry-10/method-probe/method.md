# macOS application attribution qualification

November 15, macOS 26.5.2 build 25F84, arm64. Two Wry instances (one independent contamination control) and one Electron instance ran concurrently with separate disposable profiles. Source commit and executable digests are in attribution.json. These are attribution exercises, not acceptance measurements.

## Reproduce

From the source checkout, with the renderer, release host, experimental session addon and frozen dependencies already built:

```sh
p=.ci-logs/perf-discovery-10-method
xcrun clang -O2 "$p/scan.c" -o "$p/scan"
xcrun clang -O2 "$p/coalition.c" -o "$p/coalition"
sh "$p/stage.sh"
python3 "$p/probe.py"
python3 "$p/retired.py"
```

The temporary staging copy lives outside Downloads. Jobs launched directly in Downloads initially had kernel process IDs but did not create windows or renderer helpers. Reject those snapshots. Use matched neutral staging paths; APFS copy-on-write copies are sufficient. Stage both hosts with the same Node build, lockfile, renderer and fixture bytes and record content hashes before future benchmarks. The experiment ran the installed Electron source app, not a packaged release.

## Quiescent and phase samples

1. Use one unique ephemeral interactive launchd job per app run; bootstrap in the current GUI domain with a temporary plist, disposable home/profile, RunAtLoad enabled and KeepAlive absent. Launch the host directly. A shell or automation runner in the job would add its own footprint. Keep the observer outside all measured coalitions. Capture bootstrap time and exact readiness event separately; bootstrap completion and a nonzero PID do not prove a rendered workload.
2. Read the root's resource and jetsam IDs via proc_pidinfo(PROC_PIDCOALITIONINFO = 20). The checked structure has two IDs and three reserved 64-bit fields. Corroborate with launchctl print of that exact label. Never attribute another app's process based on its name, timestamp or shared parent launchd. See the [coalition identity ABI and proc flavor](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/bsd/sys/proc_info_private.h) and [resource and jetsam index constants](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/osfmk/mach/coalition.h#L79). CLI children started normally may inherit an unrelated harness coalition, so verify a *distinct* resource coalition per host.
3. The authoritative aggregate is coalition_info_resource_usage(resource_id).phys_footprint (instantaneous bytes). The cumulative cpu_time includes retired tasks; convert ticks to nanoseconds with mach_timebase_info and report delta over the monotonic sample interval. Report CPU equivalents separately from percent of one core if applicable. This is the app's kernel-charged memory/CPU; shared OS services such as WindowServer outside the coalition are not attributed. See [Apple's usage structure](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/osfmk/mach/coalition.h#L113) and [kernel ledger rollup](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/osfmk/kern/coalition.c#L792).
4. Audit every PID separately. Enumerate with libproc; obtain both coalition IDs, parent PID, responsible PID, start-absolute-time identity and proc_pid_rusage(RUSAGE_INFO_V0) resident size, physical footprint and CPU. The SDK declares these fields in [sys/resource.h](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/bsd/sys/resource.h). Report the sum of member resident bytes as summed RSS (shared mappings may be counted in several processes), separately from physical footprint. Cross-check the target resource coalition against descendants, responsible PID and jetsam membership. Reject unexplained foreign-coalition members or missing members. Check the candidate inventory twice around each phase to detect exits and PID reuse; record all read errors. In this proof every attributed member shared both coalitions and the root's responsible PID. Scan only user-owned process metadata; compare against the resource ledger's all-user member count so unexpected hidden tasks cannot silently disappear.
5. Compare tasks_started minus tasks_exited against enumerated member count when stable. Sample the resource ledger before and after each per-process scan, using its timestamps and member counts to identify churn. If counts differ, re-enumerate within a bounded window. Record raw intervals and failures. For RSS peaks, label fixed-cadence observations as *sampled* peaks. Avoid substituting the latest resident value of an exited process. Record the UI selection and verified transcript checkpoints, process counts and active helper classes (WebContent, Networking, GPU, Node, guardian, OS services).
6. Tear down each job with bootout and attest disappearance of every observed PID/start identity. Preserve each named WebKit store's exact private UUID from the scratch profile receipt before deleting that profile, then clear only those proven synthetic stores. The initial discovery script removed disposable profile directories first; possible synthetic WebKit store remnants from those initial runs have no retained UUID and were left alone. For reproducibility the current script preserves the synthetic profile path in its receipt.

If combined ownership or metrics cannot be proved, mark that sample unqualified. On systems where private resource-ledger APIs are unavailable but ownership is independently complete, public per-process counters can still report snapshot RSS and footprint with explicit ownership coverage. CPU across exits needs an independently complete lifetime trace; live-PID deltas provide a lower bound. If XPC ownership cannot be assigned, report a partial process-tree measurement and move the gate to a dedicated supported machine; PPID-only, all-WebKit and global-system subtraction do not establish whole-app attribution.

## Results and limits

Four final concurrent observations reconciled Wry 10, Electron 6, control Wry 10 with each corresponding kernel task count. Five preexisting WebKit processes were excluded, each of the two Wry instances owned its own launchd-parented WebContent/Networking/GPU processes, and no process had overlapping attribution. All measured per-PID resource calls succeeded. The two near-simultaneous footprint views differed by at most 32,768 bytes; all three matched exactly in the last two snapshots. Every sampled app process exited after bootout. The earlier valid control run also caught app-specific audio, Safari and Electron MTL services. The retired CPU probe measured 473.52 ms coalition CPU while the live parent gained 2.71 ms and exactly one task exited. See attribution.json, attribution-first-valid.json and retired-proof.json. initial-not-ready.json records the excluded attempt. The evidence does not establish footprint reduction, stage latency, Windows behavior or any packaged-app measurement.
