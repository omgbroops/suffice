# Suffice Benchmark v1 qualification

This is a candidate benchmark foundation, not a released, validated capability benchmark or a stock-agent comparison. No harness optimization was promoted. Existing frozen campaigns and root defaults remain unchanged.

The user's workload hypothesis is still open: short repairs may not give delegation, persistent state or compaction enough useful work to repay their overhead. A complicated specification or several modules does not establish a long trajectory. Scope was classified before inference; observed duration and context are separate measurements.

## Prepared dataset and contracts

Six complete pinned real-repository task packages have public requirements, requirement-to-assertion mappings, independent Sol contract reviews, private acceptance, known references, source archives/licenses and hash receipts. Five are explicitly injected repairs, not claimed upstream bugs. Tapable is an authored new feature. Public source may have appeared in model training; no contamination-free claim is made.

All repair bases pass their authored public regression samples and fail the intended hidden checks; all reference repairs pass both. The new-feature base correctly passes four existing smoke checks while failing three public feature checks and sixteen hidden feature cases. Its reference passes all seven public and sixteen hidden checks. Four reference ablations preserve old smoke behavior but break both their targeted stage and the integration scenario. Alternative correct architectures are allowed; no grader requires particular edit counts or generated source text.

The reserve allocation preceded repair attempts. Neither reserve task has been sent to a repair actor. Evaluator authors and reviewers can see its tests; this is actor-unused reserve data, not an OS-inaccessible or contamination-free test service. Prior archived Suffice traces are development data for future policies.

## Bounded calibration

All actors used GPT-6.1 Sol low with the same nine core/navigation tools and codemode baseline. Shared credentials were read privately and refreshes kept in memory. No shared auth, dependencies or default harness code were changed. Public feature checks give this baseline executable feedback about the requested API; it still cannot run arbitrary scratch tests, a declared product-comparison limitation.

| Phase | Scheduled / attempted | Accepted patches | Complete-cost budget successes | Known API-equivalent amount | Unknown full totals |
|---|---:|---:|---:|---:|---:|
| Repair calibration | 6 / 4 | 4 | 3 | $0.1187252 | 1 |
| Staged-feature calibration | 1 / 1 | 1 | 0 | $0.0358972 | 1 |
| Combined | 7 / 5 | 5 | 3 | $0.1546224 | 2 |

Known amounts exclude engineering-agent inference and are not subscription charges or a complete total expenditure. The repair phase stopped under its frozen unknown-cost admission rule after an interrupted response recovered through retry. The separately frozen feature phase had exactly one allowed attempt and two server-overload replies; it recovered to a correct patch, but full cost remains unknown. Those two attempts are never counted as known budget successes. Per-response price stops can overshoot by one request; limits are admission/eligibility controls, not hard billing guarantees.

The first three repairs took 4–5 assistant turns and 21–25 seconds. The recovered fourth took six turns and 32 seconds. Even the staged feature took only six assistant events (including two errors), 52 seconds and 9,097 peak input-context tokens. It changed three production files rather than matching the four-module reference. It did not reach the preregistered exploratory substantial-trajectory threshold of twenty responses and 32,768 context tokens. That threshold is descriptive, not a universal definition of hard engineering.

Consequently, this preparation has **not yet established a long-horizon workload, a meaningful semantic failure rate, an efficiency improvement or a capability improvement**. Correctness was perfect in this small exposed pilot; economics are incomplete. No compaction, persistence or delegation treatment ran.

## Independent checks and an accounting finding

All five saved patches were reconstructed in new directories and passed unchanged public and hidden checks. Frozen input hashes, model/effort identity and durable usage records reconcile. Integrity passing is distinct from campaign completion: the original six-attempt repair schedule remains incomplete at four attempts.

Pi pruned one failed assistant from the final repair transcript after a successful retry: five final-history assistants versus six durable assistant events. The frozen transcript-only replayer's unknown-cost comparison consequently flagged that attempt. Its original output is retained. The supplemental receipt audit reconciles the complete durable event ledger and preserves the unknown total. Future audits must retain request/retry/assistant events, not rely only on final history.

Six focused governance/receipt tests pass. Independent reviewers approved the contracts and reviewed the runners separately. These are static model reviews plus native grader execution, not independent human authorship or exhaustive upstream regression verification. Node filesystem permissions do not by themselves deny network; no new OS/container infrastructure was created.

## Next admission target

Select coherent, larger real engineering changes with multiple dependent implementation and integration stages. Characterize scope before running, then verify that trajectories actually expose the mechanism: context pressure for compaction, state recovery for persistence, substantial implementation for delegation, distant dependencies for retrieval. Avoid artificial delays, repeated work, context padding or minimum file counts.

Keep two orthogonal tracks: preserved correctness at lower total cost, and improved acceptance at matched total budgets. Genuine baseline failures require a supported public contract and independent failure review. Do not infer difficulty from an operational error, missing telemetry or an unfair hidden assertion.

Stock Pi comes first once its native tools, environment, actual model/effort and complete usage accounting are validated. A Pi adapter with Suffice tools must be labeled accordingly. Prime and eventual Codex readiness is documented, but no external head-to-head result exists. Do not ship a task router or retry the earlier rejected optimization architectures solely on the basis of this pilot.
