## Revision-aware evidence record

Question: can a small persistent record of requirements, source evidence and executed checks avoid redundant investigation and direct verification better within the same total inference budget?

Compare A normal Sol-low navigation/testing, B a compact revision-aware evidence record, and C the same record plus bounded requirement-directed executable checks. This separates record overhead from extra verification. Keep the intervention small: code records source revisions and actual test receipts, the model supplies requirement/evidence links and unresolved questions. Do not insert changing state into old prompt bodies. Return compact append-only updates and retain full records outside context. Source/test changes invalidate affected evidence conservatively. Never infer semantic proof merely from a passing test or trust self-reported execution.

Requirements must cite the public task/API/docs or be explicitly marked assumptions. Track untested, stale, contradicted and unresolved claims; test whether the mapping itself is valid. Generated tests can be wrong: validate inputs, distinguish infrastructure/test defects from behavior failures, and never derive expected answers by copying the patch's own behavior. Independent acceptance remains outside actors. Novel test requests must not be silently suppressed by the old fixed checkpoint rule.

Measure repeat reads, fresh evidence reuse, actual record accesses, new relevant checks, failures discovered, bounded repairs, invalid generated tests and unsupported-completion rate. Count abstentions/incomplete outcomes as unsuccessful attempts. At least one mechanism test must show stale evidence cannot authorize completion after a change. A real pilot should show whether treatment actually influences behavior before a larger scored claim. Avoid embedding, new models, effort routing, pruning, rollback or extra reviewers in this experiment.
